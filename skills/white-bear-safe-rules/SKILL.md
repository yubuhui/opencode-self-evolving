# 白熊安全规则写作规范

<role>
适用于书写/改写一切给 LLM 的行为规范：全局 AGENTS.md、SKILL.md、项目 AI-开发规范.md。
依据讽刺进程理论（ironic process theory，即「白熊实验」）：负面禁令写得越醒目、越重复，越容易成为注意焦点而反弹。
本规范在不放松任何约束力的前提下，把规则写成「正面引导为主、禁令兜底」。
</role>

## 三原则

1. **禁令必配正面替代**：每条负面指令都改写为对应的正面动作（`「不要 X」`→`「应当 Y」`），被改写的负面表述只作为引用出现在「红线兜底」清单或对照参考中。
2. **行为指令与诊断信息分离**：规范正文需要点名具体被禁对象（命令名、签名、regex）属于「检测/排查」信息，放进独立的「检测签名/排查」节；行为规范正文反复念 X，反而强化对 X 的记忆。
3. **正面先行、红线兜底**：正文以正面动作开路（要做什么、怎么做）；红线（负面指令清单）集中收在文件末尾一个小节，供审计与冲突扫描使用，不进入每日常态阅读焦点。

## 改写对照表

| 原（负面） | 改写（正面） | 说明 |
| --- | --- | --- |
| `禁止用 shell 写含中文文件` | 写/改含中文文本文件一律用 Write / Edit 工具 | 正面给出唯一正确路径 |
| `禁止 Set-Content / Out-File / 重定向符` | 命令行确需写文件时用 `[System.IO.File]::WriteAllText(..., UTF8)` | 被禁命令名移入「检测签名」节 |
| `禁止一次性大改` | 大型改造拆成可独立测试/回滚的阶段，一阶段一提交 | 正面给出流程 |
| `不得为单一项牺牲另一项` | 五项原则互相约束，先找两全方案再取舍 | 正面给出决策顺序 |
| `禁止未测试就提交` | 每阶段先测试通过再提交 | 正面给出顺序 |
| `不得因技能已存在而跳过同步` | 学到的新内容一律补录，不以「技能已存在」为由省去同步 | 正面给出动作 |

## 评审清单（改写规则后自查）

- [ ] 每条负面指令是否都有对应正面替代？没有 → 补。
- [ ] 行为规范正文是否反复念被禁对象名？是 → 移入「检测/排查」节。
- [ ] 红线是否集中收尾（`## 红线兜底`）、不散落正文各处？
- [ ] 改写后约束力是否与原来完全一致（没放松、没新增）？
- [ ] `description` 触发词是否需要同步加关键词？

## 判定标准：何时触发

- 新建/修改任何 AGENTS.md、SKILL.md、开发规范文档。
- 评审代码/规则时发现规范本身是负面堆砌。
- 运行 `node check-rules.mjs`（全局正式工具）报告负面指令落在正文（红线兜底节之前）时。

## Notes

- 白熊原则：负面禁令写得越醒目、越重复，执行时越容易记起被禁对象本身。规范写作同理：禁令越显眼，越强化对它的注意。
- 本规范只改表达、不改效力：所有红线在「红线兜底」节照旧完整保留，供 `rg "禁止|一律|必须|不得"` 冲突扫描。
- 「检测签名」节天然要重复被禁对象（命令名、乱码签名、regex），属正常，不属于违反原则 2。
