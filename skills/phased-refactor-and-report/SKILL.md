# 大型改造分阶段 + 完成报告规范

<role>
适用于所有 opencode 项目的通用工程纪律：
1. 大型改造必须拆阶段实现，每阶段独立测试、独立提交 git，保证随时可回滚。
2. 非平凡任务完成后，最终回复须列出 原状 / 计划 / 实际实现 / 未按计划实现的原因。
</role>

## 判定标准：什么算「大型改造」

满足任一即触发分阶段流程：
- 涉及 3 个以上文件的改动
- 跨越 2 个以上模块/子系统（前后端、共享库、数据库迁移等）
- 改动核心共享代码（路由、数据通道、公共组件、构建链）
- 预期 2 个以上逻辑变更点（非单点修 bug）
- 高风险：影响现有数据、破坏兼容、不可简单回滚

## 一、大型改造分阶段规范

### 规划阶段（动手前先给计划）

1. 先完整分析现状，输出《改造计划》：整体目标 + 阶段拆分。
2. 拆分原则：
   - 每阶段可**独立测试**、可**独立提交**、失败可**独立回滚**。
   - 每阶段尽量只做一类变更（先改结构/后改行为，先加后删）。
   - 阶段粒度不宜过大：理想情况每阶段 1 次 commit。
3. 计划中写明每阶段的：目标、涉及文件、验证方式（测试命令/手动步骤）。

### 执行阶段（每阶段固定循环）

每阶段严格按 `实现 → 测试 → 提交` 顺序：

1. **实现**本阶段范围，不越界带入下阶段内容。
2. **测试**：跑该阶段的验证（lint/单测/类型检查/冒烟），失败则回到 1 修复，不得带病进入下阶段。
3. **提交**：本阶段全部通过后提交 git，提交信息标注阶段（如 `feat: 阶段1/3 - 数据层迁移`）。
4. 提交后仓库保持「绿」：随时可从该 commit 继续，出问题可回退到上一阶段。

### 中途发现计划外事项

- 发现计划外需求/阻塞：**暂停**，向用户说明并更新计划，不擅自扩阶段。
- 阶段需要重排/合并/新增：先更新计划再继续。

## 二、任务完成报告规范

非平凡任务（含全部大型改造）完成后，最终回复必须包含四要素报告：

| 维度 | 内容 |
| ---- | ---- |
| 原状 | 任务前基线：涉及哪些文件、原有行为/结构是什么 |
| 计划 | 计划做什么：目标、阶段划分、预期结果 |
| 实际 | 实际做了什么：哪些文件/行为变了，验证结果 |
| 偏差原因 | 未按计划实现的部分 + 原因（技术阻碍/需求变化/发现更优解等）；无偏差写「无」 |

报告「实际」列若涉及页面/模块/命令/架构变更，附一句「技能同步情况」（已更新 `xxx` / 无需更新）——见 `auto-skill-creator` 技能同步更新规范。

小型任务（单文件小改动、纯问答）可豁免，但给一句话结果说明即可。

## 关键命令 / 模式

- 每阶段提交前必跑项目 lint/typecheck/test（先查 AGENTS.md / package.json 确定命令）。
- 提交粒度：一阶段一 commit，commit message 带阶段标识。
- 回滚：`git log` 定位阶段 commit，`git revert <commit>` 精确回退单阶段。

## 注意事项（红线）

- 禁止一次性大改不拆分（无法回滚、无法定位问题）。
- 禁止未测试就提交、禁止带测试失败进入下一阶段。
- 禁止完成报告跳过「偏差原因」列（用户要求豁免除外）。
- 大型改造开始前必须先出计划并经用户确认（用户明确指示直接做除外）。
