# 测试总控与完成门禁

<role>
适用于所有项目的通用测试总控：从验收依据和改动风险决定测什么、调用哪些方法、怎样执行，并依据覆盖与证据判断完成。执行顺序为 P1 探测与分级 → P4 划影响范围 → P2 场景与验证计划 → 执行/P5 处理失败 → P3 完成门禁。
</role>

## 三层职责与按需读取

1. **总控**：本技能负责范围、风险、方法选择、执行结果与完成结论。
2. **专项**：[场景设计](../test-scenario-design/SKILL.md) 推导用例及独立预期；[界面验证](../ui-test-verification/SKILL.md) 指导真实渲染与操作。只读取本次风险涉及的专项与参考文件。
3. **项目执行**：项目技能/规范提供真实命令、测试数据、运行环境、界面入口和业务契约。

`plan-review` 复核开工计划，其中的测试计划承接 P2；`phased-refactor-and-report` 负责阶段与提交节奏，本技能提供其测试和证据门禁。

## P1 探测测试栈、验收依据与风险

1. 查项目 AGENTS、技能索引、测试目录、CI、构建/测试配置及依赖声明。按实际语言查看 `package.json`、`pyproject.toml`、`go.mod`、`Cargo.toml`、`pom.xml`、解决方案等入口，并定位真正的测试脚本与配置。
2. 记录工作目录、真实命令、过滤方式、测试环境/服务、数据准备与已有用例。关键功能或疑似既有失败时，修改前执行相关基线或建立缺陷复现。
   应用运行验证同时定位浏览器控制台/异常/网络与相关开发、后端、IDE任务输出，确认采集能力与目标；导航、启动及关键操作前建立覆盖，详见 [运行时错误巡检](references/runtime-diagnostics.md)。
3. 从需求、接口/组件契约和缺陷描述明确成功/拒绝/失败恢复标准与关键不变量；区分已确认预期与待确认假设。
4. 缺少自动化入口时，采用可复现的手动步骤或最小可行验证。关键行为仍无法验证时记录缺失条件并标为阻塞/未验证。
5. 按影响与回归风险选择验证强度：

| 风险 | 典型特征 | 投入方式 |
| --- | --- | --- |
| 低 | 可逆文案、注释、局部样式等，行为和数据影响有限 | 复用现有检查并针对性核对；存在内容/布局影响时做相应真实界面检查。 |
| 中 | 单个业务功能、输入规则、局部交互或缺陷修复 | 正常行为及适用边界、异常、状态场景；新增用例针对有效覆盖缺口。 |
| 高 | 共享核心、存储/删除、异步并发、批量、迁移等 | 显式不变量、关键失败恢复及状态组合；按实际风险补接口/持久化/跨层证据和相关回归。 |

风险由具体影响决定，可根据发现更新。验证强度与任务规模相称，已有有效覆盖优先复用。

## P2 定每阶段验证命令（先设计场景，对接计划复核）

每阶段形成「验收项/风险 → 场景 → 预期结果 → 真实命令或手动步骤 → 证据」映射。先分析适用维度，再选择验证层与执行入口。

### 专项路由

| 风险信号 | 调用方法 | 交付结果 |
| --- | --- | --- |
| 输入、约束、正常/异常路径、缺陷复现 | `test-scenario-design` → 基础设计参考 | 等价类、边界、异常恢复与独立预期。 |
| 状态变化、重复提交、快速切换、并发数据 | 场景设计 → 状态与一致性参考 | 转换/事件顺序、冲突契约、最终数据与副作用断言。 |
| 解析/导入、随机输入、极端操作 | 场景设计 → 模糊与压力参考的输入部分 | 输入模型、固定 seed、预算、正确性性质、失败复现。 |
| 批量、容量、资源或性能风险 | 场景设计 → 模糊与压力参考的压力部分 | 目标负载、环境、指标、阈值、停止条件和恢复检查。 |
| 内容展示、弹窗/容器、滚动、缩放、交互 | `ui-test-verification`，需要时叠加状态方法 | 真实渲染、全文/操作可达、动态组合及业务结果。 |
| 应用启动、导航或关键操作，包括表面成功的场景 | [运行时错误巡检](references/runtime-diagnostics.md) | 控制台/异常/网络/进程的前置采集、主动读取、分类及处置证据。 |

非平凡行为改动先用场景设计检查正常、边界、异常、状态、重复并发、输入扰动、容量与 UI 的适用性；只展开相关方法，重要不适用项说明理由。小改动用最小充分验证即可。

### 从场景到执行

- 逻辑规则选对应单元层，模块/接口/存储协作选集成层，布局与完整用户操作选真实浏览器/端到端层。一个测试层只为它实际覆盖的行为提供证据。
- 项目已有测试规范时沿用其工具和组织方式；为缺陷、重要新行为和真实覆盖缺口补有效用例。断言指向契约与可观察结果，详见场景设计 D4。
- 静态检查、构建、类型检查按真实项目命令执行，作为对应层证据。
- 文档/技能改动：项目内执行 `node C:/Users/huang/.config/opencode/audit-docs.mjs --changed`；全局规则库执行 `npm test` 与 `node audit-docs.mjs --changed`。参考文件还需按实际工具覆盖情况核对链接、编码及规则；判级见 `docs-stale-audit`。
- 用例字段复用场景设计的模板，阶段汇总使用 [验证记录](references/verification-record.md)。简单任务可用等价的简短记录。

命令标明工作目录和目标范围，手动步骤给出输入、操作与期望。环境准备、隔离/清理、异步等待和随机预算按专项方法落实。

### 执行中的主动巡检

应用运行场景在启动后、关键操作后及完成前主动读取适用来源，复用当前验证动作做有界增量检查。界面正常或命令成功时同样执行。核对采集时间窗、准确目标、截断/丢弃与覆盖缺口；分类本次异常、预期失败、既有问题及无关噪声，处理后重演并复读。纯文档/静态任务没有运行场景时记录不适用原因。详细步骤单一来源为运行时错误巡检参考。

## P3 完成前测试门禁（Definition of Done）

声明完成前逐项核对：

1. **覆盖**：相关验收项和高风险场景有实际结果，包含适用的边界、异常、状态/交互；关键预期已明确。
2. **有效执行**：命令或手动步骤已执行，目标环境/用例正确。对测试运行器核对发现数、执行数、失败/取消/跳过及过滤范围；零用例或关键跳过保持未验证，补测后再判定。
3. **证据**：断言覆盖正确结果、状态与副作用。真实 UI、真实协议/事务及性能结论分别有相应层证据。运行场景附主动巡检结果：适用来源与窗口有效，相关非预期错误已处理，预期异常和噪声有判定依据；必要来源缺失仍属未验证/阻塞。
4. **结果**：本次受影响验证和项目要求的门禁通过。失败按 P5 处理；环境缺失、关键验收未执行或必要门禁受阻时明确标为阻塞/未验证。
5. **披露**：报告实际范围、方法、计数、结果、证据和剩余风险。既有基线失败单列并提供归因依据，结论限定于已验证范围。

静态/文档检查按预期检查对象与诊断计数验收，手动验证按具名场景结果验收；测试运行器的用例计数与这两类检查分别记录。存在目标改动却扫描到零目标时，先核对选择范围。

四态结论：**通过**＝已执行且满足预期；**失败**＝已执行且不符预期；**阻塞**＝缺少环境/依赖/明确契约等必要条件；**未验证**＝场景适用但尚无有效执行证据。

## P4 受影响范围判定

- 用 `git status --short`、`git diff HEAD --name-only` 和未跟踪文件列出改动；非 Git 项目依据明确的改动清单。
- 从文件追到调用方、共享组件/状态、接口、存储、配置与用户路径；判断是否影响相邻行为、契约或兼容性。
- 边界内改动先跑目标场景与对应回归；共享/核心改动扩展到相关使用方和必要跨层回归。全量执行以项目门禁及真实影响为依据。
- 范围内检查通过后结束验证。新代码变更、失败、环境变化或未解风险出现时，再补充/重跑受影响检查，并记录原因。

## P5 测试失败循环与归因

1. 保存命令、失败断言、输入、环境和必要日志；主动巡检发现的相关错误同样进入定位流程，即使功能表面成功。先用最小失败用例或事件序列定位。
2. 分类处理：

| 类别 | 处理与结论 |
| --- | --- |
| 本次回归或相关缺陷 | 修复行为，优先建立能复现缺陷的回归用例；重测失败场景和受影响范围，通过后推进。 |
| 环境/依赖问题 | 修复测试环境或采用能验证同一验收项的替代方法；覆盖不到的关键项保持阻塞。 |
| 既有基线失败 | 用修改前结果、相同环境的基线复现等证据确认；独立记录归因。受影响关键验证和项目必要门禁仍须满足。 |
| 不稳定/时序失败 | 保留全部失败信息，检查共享数据、等待、时钟和竞态；固定输入/seed/事件序列定位，再针对性重测。 |

3. 测试预期发生合理变化时，以已确认的需求/契约修正用例，保留仍有效的行为断言。
4. 每次修复后按 P4 更新验证范围；运行时错误重做触发操作、重读对应来源并核对业务结果，保留前后证据。验证通过再进入下一阶段或完成，无法解决的关键问题如实报告阻塞和缺口。

## 经验回流

漏测缺陷 → 漏掉的风险/场景 → 可复现回归 → 方法更新。通用推导方法更新对应专项，项目命令与业务数据留在项目技能；description、INDEX 及关联规则按 `auto-skill-creator` 同步。测试产物遵循项目隔离和 `powershell-utf8-safety` 编码规则。

## 红线兜底

- 先明确风险、场景和独立预期，再执行真实验证；不得以流程走完、退出码为零或用例数量替代覆盖与正确性判断。
- 本次受影响验证及项目必要门禁通过后再完成；不得把未执行、零用例、关键跳过或阻塞标为通过。
- 测试断言业务行为，低风险可逆改动优先复用验证；不要机械补实现镜像测试或无风险依据地反复扩大全量测试。
- 对失败保留证据、归因、修复和重测；不得通过删断言、跳过关键用例、放宽阈值或只保留重试成功结果掩盖失败。
- 基线异常明确披露且满足当前必要门禁；不得把既有失败自动视作通过，或把局部验证说成全项目通过。
- 运行验证主动检查适用控制台、网络和进程输出；不得仅凭页面正常、命令成功或未采集到日志宣告无运行时错误。
