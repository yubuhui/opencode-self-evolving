# 轻量测试总控与完成门禁

<role>
从本次改动的直接路径、已知缺陷和项目必要门禁起步，用可重复核验的结果判断完成。具体风险决定追加方法，主观视觉与体验交人工。执行顺序为 P1 明确依据 → P4 划范围 → P2 选择验证 → 执行/P5 处理失败 → P3 判定完成。
</role>

## 三层职责与按需读取

1. **总控**：本技能负责范围、风险、方法选择、执行结果与完成结论。
2. **专项**：[场景设计](../test-scenario-design/SKILL.md) 是按需方法库；[界面验证](../ui-test-verification/SKILL.md) 验证有明确契约的真实交互。只读取具体风险需要的内容。
3. **项目执行**：项目技能/规范提供真实命令、测试数据、运行环境、界面入口和业务契约。

`plan-review` 复核开工计划，其中的测试计划承接 P2；`phased-refactor-and-report` 负责阶段与提交节奏，本技能提供其测试和证据门禁。

## P1 明确入口、预期与投入

1. 从项目 AGENTS、技能索引及真实测试配置定位相关已有用例、命令和明确的必要门禁。按实际语言查看 `package.json`、`pyproject.toml`、`go.mod` 等入口，已有准确项目记录优先复用。
2. 从需求、接口/组件契约和缺陷描述确定直接验收路径、独立预期及相关不变量。关键预期有歧义时确认；美观、协调、自然度、舒适度等主观项目交人工。
3. 明确工作目录、目标用例和必要环境。关键功能或疑似既有失败时，修改前执行相关基线或建立缺陷复现。缺少自动化入口时采用可复现手动验证，必要条件缺失标为阻塞。
4. 复用已有有效覆盖，按具体影响选择投入：

| 风险 | 典型特征 | 投入方式 |
| --- | --- | --- |
| 低 | 可逆文案、注释、局部样式，行为和数据影响有限 | 针对性核对及适用已有检查；有具体布局风险时追加对应真实操作。 |
| 中 | 单个业务分支、输入规则、局部交互或缺陷修复 | 直接路径、已知复现和受影响约束；额外场景以目标缺陷为依据。 |
| 高 | 金额、删除、共享核心/写入、迁移等 | 核对相关不变量、失败一致性与使用方；真实时序、重复副作用或冲突风险触发对应方法。 |

项目必要门禁来自当前适用的项目规范、CI要求或明确维护约定；测试脚本存在本身仅表示可用入口。每项追加检查用一句话说明具体风险或门禁依据。

## P2 选择最小充分验证

从直接路径和已知缺陷选择现有快速检查，再补真实覆盖缺口。用简短记录说明「验收项/风险 → 预期 → 命令或操作 → 结果」，必要时展开专项。

### 专项路由

| 风险信号 | 调用方法 | 交付结果 |
| --- | --- | --- |
| 修改约束/业务分支，存在相关拒绝或失败一致性风险 | 场景设计 → 基础设计参考 | 对应等价类、边界或异常恢复，独立预期。 |
| 修改请求归属、状态转换、共享写入，或已知重复/时序缺陷 | 场景设计 → 状态与一致性参考 | 相关事件顺序、冲突契约、最终数据及副作用。 |
| 修改解析/导入，存在复杂输入探索需求 | 场景设计 → 模糊与压力的输入部分 | 优先相关合法/畸形样本；随机探索另定目标、seed和预算。 |
| 性能敏感改动、已知容量问题或明确性能要求 | 场景设计 → 模糊与压力的压力部分 | 目标负载、阈值来源、指标及停止条件。 |
| 改变交互，或有具体内容/布局/操作可达性风险 | `ui-test-verification` | 受影响的真实操作、契约断言与必要数据结果。 |
| 已实际启动应用或执行用户操作 | [运行时信号检查](references/runtime-diagnostics.md) | 复用运行检查相关来源，发现问题后定位、修复和重演。 |

只展开已触发的方法，未触发专项属于范围外。截图在具体视觉问题定位、取证或用户要求时选用，常规证据优先操作断言、日志与数据。

### 从场景到执行

- 逻辑规则选对应单元层，模块/接口/存储协作选集成层，布局与完整用户操作选真实浏览器/端到端层。一个测试层只为它实际覆盖的行为提供证据。
- 项目已有测试规范时沿用其工具和组织方式；为缺陷、重要新行为和真实覆盖缺口补有效用例。断言指向契约与可观察结果，详见场景设计 D4。
- 静态检查、构建、类型检查按改动风险和项目必要门禁选择真实命令，作为对应层证据。
- 文档/技能改动：项目内执行 `node C:/Users/huang/.config/opencode/audit-docs.mjs --changed`；全局规则库执行 `npm test` 与 `node audit-docs.mjs --changed`。参考文件还需按实际工具覆盖情况核对链接、编码及规则；判级见 `docs-stale-audit`。
- 默认使用 [验证记录](references/verification-record.md) 的简短形式；复杂场景再选择扩展字段。

命令标明工作目录和目标范围，手动步骤给出输入、操作与期望。环境准备、隔离/清理、异步等待和随机预算按专项方法落实。

### 执行中的相关运行信号

实际运行时主动读取与本次行为相关的控制台、请求或进程输出，表面正常时同样检查；可合并检查节点，复用已有采集。按结论需要确认目标、时间窗和完整性，发现相关错误后再展开诊断。纯文档/静态任务执行对应检查。必要来源缺失时限定结论并记录对应缺口，细节见运行时信号检查参考。

## P3 完成前测试门禁（Definition of Done）

声明完成前逐项核对：

1. **覆盖**：直接验收项、已知缺陷和具体风险触发的必要场景有实际结果，预期明确。
2. **有效执行**：命令或手动步骤已执行，目标环境/用例正确。对测试运行器核对发现数、执行数、失败/取消/跳过及过滤范围；零用例或关键跳过保持未验证，补测后再判定。
3. **证据**：断言覆盖结果与相关状态/副作用；UI、协议/事务及性能结论有相应层证据。实际运行已检查相关信号并处理非预期错误，缺少必要证据保持未验证/阻塞。
4. **结果**：本次受影响验证和项目要求的门禁通过。失败按 P5 处理；环境缺失、关键验收未执行或必要门禁受阻时明确标为阻塞/未验证。
5. **披露**：简述范围、实际检查、结果和必要缺口，附对应计数/证据；既有基线失败单列。主观项目记为未验证（待人工），给简短验收入口与关注点。

静态/文档检查按预期检查对象与诊断计数验收，手动验证按具名场景结果验收；测试运行器的用例计数与这两类检查分别记录。存在目标改动却扫描到零目标时，先核对选择范围。

四态结论：**通过**＝已执行且满足预期；**失败**＝已执行且不符预期；**阻塞**＝缺少环境/依赖/明确契约等必要条件；**未验证**＝场景适用但尚无有效执行证据。

缺口仅列当前验收范围内的项目。客观检查和必要门禁通过即可结束 AI 验证；还有人工项目时，交付结论写明「AI 检查通过，体验待人工验收」，整体验收保持待确认。

## P4 受影响范围判定

- 用 `git status --short`、`git diff HEAD --name-only` 和未跟踪文件列出改动；非 Git 项目依据明确的改动清单。
- 从文件追到调用方、共享组件/状态、接口、存储、配置与用户路径；判断是否影响相邻行为、契约或兼容性。
- 边界内改动先跑目标场景与对应回归；共享/核心改动扩展到相关使用方和必要跨层回归。全量执行以项目门禁及真实影响为依据。
- 所选检查与项目必要门禁通过后结束验证。新代码变更、失败、影响结果的环境变化或未解风险才触发追加，并记录具体原因。

## P5 测试失败循环与归因

1. 保存命令、失败断言、输入、环境和必要日志；主动巡检发现的相关错误同样进入定位流程，即使功能表面成功。先用最小失败用例或事件序列定位。
2. 分类处理：

| 类别 | 处理与结论 |
| --- | --- |
| 本次回归或相关缺陷 | 修复行为，优先建立能复现缺陷的回归用例；重测失败场景和受影响范围，通过后推进。 |
| 环境/依赖问题 | 修复测试环境或采用能验证同一验收项的替代方法；覆盖不到的关键项保持阻塞。 |
| 既有基线失败 | 用修改前结果、相同环境的基线复现等证据确认；独立记录归因。受影响关键验证和项目必要门禁仍须满足。 |
| 不稳定/时序失败 | 保留全部失败信息，检查共享数据、等待、时钟和竞态；固定输入/seed/事件序列定位，再针对性重测。 |

3. 测试预期发生合理变化时，以已确认的需求/契约修正用例，保留仍有效的行为断言。
4. 每次修复后按 P4 更新验证范围；运行时错误重做触发操作、重读对应来源并核对业务结果，保留前后证据。验证通过再进入下一阶段或完成，无法解决的关键问题如实报告阻塞和缺口。

## 经验回流

漏测缺陷 → 漏掉的风险/场景 → 可复现回归 → 方法更新。通用推导方法更新对应专项，项目命令与业务数据留在项目技能；description、INDEX 及关联规则按 `auto-skill-creator` 同步。测试产物遵循项目隔离和 `powershell-utf8-safety` 编码规则。

## 红线兜底

- 先明确风险、场景和独立预期，再执行真实验证；不得以流程走完、退出码为零或用例数量替代覆盖与正确性判断。
- 本次受影响验证及项目必要门禁通过后再完成；不得把未执行、零用例、关键跳过或阻塞标为通过。
- 测试断言业务行为，低风险可逆改动优先复用验证；不要机械补实现镜像测试或无风险依据地反复扩大全量测试。
- 对失败保留证据、归因、修复和重测；不得通过删断言、跳过关键用例、放宽阈值或只保留重试成功结果掩盖失败。
- 基线异常明确披露且满足当前必要门禁；不得把既有失败自动视作通过，或把局部验证说成全项目通过。
- 运行验证主动检查相关来源；不得仅凭页面正常、命令成功或空日志宣告无运行时错误。
- 主观视觉与体验交人工验收；不得把 AI 看图意见当作客观缺陷反复修改，或把待人工项目标为通过。
- 专项由具体风险触发，通过即停止；不得把方法库全表、截图或完整记录模板设成每次任务的默认清单。
