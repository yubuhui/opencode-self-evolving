# 测试场景设计

<role>
把功能要求和改动风险转成可验证的场景，回答「为什么测、怎样构造、什么才算正确」。总控与完成结论由 [test-verification](../test-verification/SKILL.md) 负责；界面实测由 [ui-test-verification](../ui-test-verification/SKILL.md) 负责；项目技能提供真实命令、数据和操作入口。
</role>

## 何时使用

- 新增或修改业务行为、输入约束、存储、接口、异步交互与共享逻辑。
- 修复缺陷，需要能抓住该缺陷的回归场景。
- 现有验证以顺利路径为主，需要审视边界、失败恢复或状态组合。
- 用户要求评估测试充分性、边界、极端操作、模糊或压力场景。

可逆低风险小改动优先复用现有检查，按实际风险做针对性核对。已有充分覆盖时复用用例，新增测试集中于业务行为、回归缺口和高风险组合。

## D1 明确验收依据与不变量

1. 读取需求、项目规范、接口契约、缺陷复现步骤及相关用例；列出功能承诺、约束单位、支持范围和允许的失败行为。
2. 把正确结果写在测试步骤之前。预期优先来自需求、规范样例或独立计算；实现代码用于发现分支与风险。
3. 提取不变量：例如同一逻辑提交产生一次约定副作用、失败后已确认数据保持一致、切换对象后界面归属当前对象。
4. 关键预期有歧义时，列出待确认问题。示例契约与项目已确认契约分别标明；结论依赖的假设须披露。

## D2 按风险选择方法

先逐项判断适用性，再展开相关方法。非平凡任务记录高风险项和重要不适用理由；小改动可以用几行说明。

| 方法 | 触发信号 | 重点与参考 |
| --- | --- | --- |
| 正常路径/等价类 | 新功能、不同输入类型或业务分支 | 各类代表值及可观察结果，见 [基础设计](references/scenario-design.md)。 |
| 边界 | 数量、范围、长度、页数、时间、容量限制 | 边界内/边界上/边界外，含空值与单位差异，见基础设计。 |
| 异常与恢复 | 外部依赖、校验、文件、存储、网络操作 | 在失败点注入故障，验证反馈、数据、清理和重试，见基础设计。 |
| 状态与时序 | 加载、编辑、保存、关闭、切换、撤销 | 状态转换、操作顺序、过期响应，见 [状态与一致性](references/state-consistency.md)。 |
| 重复/并发 | 重试、连点、多窗口、共享记录、批处理 | 按契约验证副作用次数、冲突处理及最终持久化结果，见状态与一致性。 |
| 输入扰动/模糊 | 解析、导入、格式转换、复杂输入面 | 结构化畸形输入、固定 seed、失败最小化，见 [模糊与压力](references/fuzz-and-stress.md)。 |
| 容量/压力 | 批量、长列表、性能目标、资源限制 | 数据规模、到达率、并发数与资源预算分别设计，见模糊与压力。 |
| 布局/交互 | 页面、弹窗、容器、输入与内容显示 | 长内容、空间、缩放、状态组合和实际操作，转入 UI 专项。 |

“暴力测试”作为需求描述时，先明确是畸形输入、随机操作、重复并发，还是资源压力，再选对应方法。前后端都按功能风险选方法。

## D3 推导最小充分场景集

1. 先写一个可证明主要行为的正常场景，再列约束边缘、失败点、状态转换与高风险副作用。
2. 从适用参考方法推导场景；每个场景明确目标缺陷，合并验证目标相同的重复用例。
3. 对容易相互影响的维度显式组合，如「小窗口＋错误提示」「保存中＋切换对象」「提交成功但响应丢失＋重试」。
4. 组合很多时用风险排序与成对覆盖缩减；已知耦合和高风险三维组合单独验证。抽样范围与未覆盖部分写入记录。
5. 缺陷修复优先建立失败复现：用修复前版本或受控复现证明用例能抓到问题，再验证修复结果；无法重现时如实记录证据限制。

## D4 落实验证层与测试质量

- 纯计算/规则用单元层；真实模块、序列化、事务或接口协作用集成层；用户完整操作和布局用浏览器/端到端层。以能抓住目标缺陷的最低充分层为主，跨层风险补对应集成证据。
- 断言用户或调用方可观察的结果、契约和副作用。共享正确性依据来自需求或独立样例；测试中的期望值与被测算法保持独立。
- 测试数据使用隔离账户、临时目录/数据库或唯一标识；注明初态、时钟/时区、seed、依赖版本等相关条件，执行后清理并验证可重复运行。
- Mock 放在当前测试边界之外的依赖，用于控制失败和时序；边界协议、持久化、真实布局等风险保留对应真实集成验证。
- 异步验证等待可观察条件并设超时；并发次序通过可控屏障/延迟建立，失败保留事件顺序。

## D5 输出与交接

使用 [统一场景模板](references/scenario-design.md)，输出「风险→场景→预期→方法」映射、数据/环境需求及优先级；执行后补实际结果与证据。

设计完成的标准：适用高风险均有具名场景，预期可判定，执行入口真实可用或明确标为阻塞。场景设计完成与应用验证完成分别记录，执行与最终门禁回到总控。

## 红线兜底

- 预期依据需求、契约与独立样例；不得复制被测实现来计算期望值或以「没有崩溃」代替正确性断言。
- 方法按适用风险展开；不得按前后端或错误可见性排除某类测试，也不得把所有专项机械用于每个小改动。
- 缺陷与高风险行为优先建立有效回归；不要为低风险可逆改动或实现细节机械补测试。
- 场景设计、实际执行、证据结论分别记录；未执行或关键预期未明确时，不得声称对应行为验证通过。
